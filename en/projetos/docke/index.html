Why it exists

The group was going to migrate all its documentation to the cloud. I developed Docke to meet the key points of that migration, shaped to the teams’ routine.

02

Problem, system, and proof

Problem

Documents from multiple companies to organize in the cloud, with deadlines and legal retention.

System

Electronic document management for multiple companies: search in scanned text (OCR), compliance deadlines, legal retention, and a hash-chained audit trail.

Proof

89 tests

83 backend and 6 end-to-end, on GitHub Actions. Checked on 9 Nov 2026.

04

How it was built

Architecture

The React frontend talks to a FastAPI API, which stores data in Supabase's PostgreSQL and files in Cloudflare R2. The browser sends the file straight to R2; the API only confirms the upload and creates an OCR job. A background worker reads the file, extracts the text with Tesseract, and writes it to the document, where Postgres full-text search finds it.

Technical decisions

  1. Company isolation in the database itself

    Each user request opens a transaction, passes the JWT claims to Postgres with set_config('request.jwt.claims'), and switches role with SET LOCAL role authenticated. So the Row Level Security policies apply to every query on that connection, and access by company or folder is blocked by the database, not just by the API. SET LOCAL only lasts inside an explicit transaction, so the whole request runs inside one. Admin operations and the worker use a separate connection that bypasses RLS and checks permissions in code.

    View in code: dependencies.py L251–288 README.md L20 README.md L50 20260627000003_rls_policies.sql dependencies.py L291–295

  2. Files go straight to storage

    The browser uploads the file to R2 through a presigned URL, in 10 MB parts from 20 MB up. Then the API checks the real size with a HEAD request, because the URL doesn't enforce a limit, and computes the SHA-256. If the company already has an identical file, the API returns 409 and deletes the object and the pending record, so no garbage is left in the bucket.

    View in code: README.md L51 Documents.tsx L400–401 Documents.tsx L462–463 documents.py L224–266 storage_service.py L117–137 documents.py L321

  3. OCR in a queue inside Postgres

    Confirming the upload writes a job to the ocr_jobs table, and a worker takes the oldest one with FOR UPDATE SKIP LOCKED, so multiple workers don't compete for the same job. A job stuck in processing for more than 10 minutes goes back to the queue, up to 3 attempts; after that it stays failed. Tesseract reads Portuguese and English; for images, after preprocessing with OpenCV.

Challenge

Verifying the trail by links, not timestamps

Each event stores an HMAC-SHA256 computed over its content and the hash of the company's previous event. The first verification sorted events by timestamp and reported a broken chain with no tampering, because events in the same transaction share a timestamp. I rewrote the verification to follow the links from the first event. The end was still uncovered: deleting the most recent event went unnoticed; now the last stored hash must exist, or the trail shows as truncated.

Testing

The backend has 83 tests collected by pytest, from 30 functions (one of them runs 50 times); the integration tests run against a local Supabase and cover company isolation through RLS, permissions, OCR, share links, and the trail flagging an event that was altered, deleted, or cut off at the end. The 6 Playwright tests sign in to the demo, switch identities, open a PDF, and search. GitHub Actions runs both on every push to main.
