01

Por que existe

Sempre tive dificuldade de controlar as minhas finanças. Preencher planilhas era chato e cansativo, e os apps cobravam mensalidades que eu não queria pagar. Então desenvolvi o meu próprio organizador de finanças, voltado para as minhas necessidades, juntando o melhor das ferramentas que conhecia.

02

Problema, sistema e prova

Problema

Planilha cansativa de preencher; aplicativo com mensalidade.

Sistema

Finanças pessoais com categorização automática em 3 camadas (regras, cache e um modelo de linguagem); importa extratos de 4 bancos, OFX e CSV.

Prova

298 testes

250 de backend, 8 de frontend e 40 de ponta a ponta. Conferidos em 9/11/2026.

04

Como foi construído

Arquitetura

Separei o FlowTrack em três partes: o frontend em React 19 e TypeScript, uma API REST em FastAPI (/api/v1) e o banco PostgreSQL no Supabase, com Row Level Security. A API grava cada transação na hora e, se ela vier sem categoria, coloca um item na tabela categorization_queue. Um worker, chamado pela rota interna /internal/process-queue, categoriza a fila em lotes de 20. No modo demonstração, o Axios troca a rede por uma API em memória no navegador.

Ver no código: README.pt-br.md L60–82 imports.py L67–88 internal.py L15–19 claude_api.py L78–95 services.ts L25–34

Decisões técnicas

  1. Categorização numa fila, fora da importação

    A importação não espera a IA: cada transação sem categoria vira um item pending na categorization_queue, e o worker processa a fila de 20 em 20 quando a rota interna é chamada. Na ADR 0004 registrei o motivo: a importação fica imediata, e a categoria chega depois. A consequência visível é que a transação aparece sem categoria até a próxima rodada; se a chamada ao modelo falhar, o item é marcado como failed e o lote segue.

    Ver no código: transactions.py L71–74 imports.py L84–88 claude_api.py L78–95 claude_api.py L226–231 0004-ai-categorization-pipeline.md

  2. O modelo responde por uma ferramenta (tool use)

    Na terceira camada, o Claude Haiku não responde em texto livre: o tool_choice força a ferramenta categorize, cujo esquema limita a categoria às permitidas para aquela pessoa e a confiança a valores de 0 a 1. Mesmo assim, o worker confere a resposta: categoria fora da lista não é gravada, confiança inválida vira 0, abaixo de 0,85 a transação vai para A revisar, e só a resposta a partir desse corte entra no cache.

    Ver no código: claude_api.py L30–64 claude_api.py L178–219 _helpers.py L167–170 0004-ai-categorization-pipeline.md

  3. Demonstração inteira no navegador

    A demonstração pública usava uma conta real num projeto gratuito do Supabase; quando o projeto foi pausado por inatividade, ela saiu do ar. Por isso, no modo demonstração, o interceptor do Axios troca o transporte por um adaptador que atende /api/v1/* com uma implementação em memória, guardada no sessionStorage. As páginas não sabem a diferença. O custo, registrado na ADR 0006, é manter as regras de negócio duas vezes, em Python e em TypeScript.

    Ver no código: 0006-in-browser-demo.md services.ts L30–34 index.ts L34–44

Desafio

Chave service_role sem misturar dados de usuários

A API acessa o banco com a chave service_role, que ignora o RLS. Então cada rota confere o dono: _require_account e _require_category devolvem 404 para conta ou categoria de outra pessoa. O worker só lê a transação do dono do item da fila e só oferece ao modelo as categorias padrão e as dele. Para provar isso, escrevi um Supabase em memória (fake_supabase.py) cujos filtros filtram de verdade, e testei um usuário tentando alcançar os dados de outro.

Ver no código: _helpers.py L24–42 claude_api.py L67–75 claude_api.py L114–122 fake_supabase.py L1–6 test_security.py L1–5 test_security.py L322–355

Testes

São 250 testes de backend com pytest, inclusive de autorização entre usuários e do worker com um Claude falso; 8 de frontend com node --test, sobre a exportação CSV e a fila offline; e 40 de ponta a ponta com Playwright: 20 cenários rodados no computador e no celular, contra um build local da demonstração. O GitHub Actions roda tudo a cada push no main e em pull requests e, depois dos E2E, mede o contraste dos selos.

Ver no código: README.pt-br.md L141–154 test_ai_categorization.py syncQueue.test.ts export.test.ts playwright.config.ts L27–30 test.yml e2e.yml
